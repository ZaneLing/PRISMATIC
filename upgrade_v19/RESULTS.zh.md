# v0.19：订单真实写入与工具技能进化

## 已完成的工程实验

对同一份合成药物订单，在本地真实 FHIR 服务执行两种结构的写入与回读。

| 订单结构 | 创建状态 | 回读状态 | 剂量相关字段完整保留 |
|---|---:|---:|---|
| 原基准的途径字符串 | 201 | 200 | 否 |
| 途径转为 CodeableConcept 文本 | 201 | 200 | 是 |

FHIR R4 的途径字段要求 CodeableConcept。转换器原样保留途径文字，不猜测术语编码。原基准 rate 字段出现类似时长的单位时，保留并标记语义未核验，不把它自动解释为有效给药速度。[FHIR R4 剂量字段定义](https://hl7.org/fhir/R4/dosage-definitions.html#Dosage.route)。

第二个真实探针主动触发字段丢失，核验后删除本次新建资源，并在原动作预算内返回修复反馈；全部资源数量恢复原值。这是零模型调用的合成工程实验，不充当 agent 成功率。

病例串行执行以避免状态互相干扰，完全相同代码/病例/技能已真实执行的轨迹可缓存重放。GT 字段不进入 actor 提示；训练反馈的患者编号被替换。官方任务切分存在患者重叠，不宣称患者独立。

完整 agent 实验在 Gemini 和中间技能评价后执行，未完成成绩不报告。协议及真实工程检查见 `protocol.json` 和 `results/`。

## 开发集发现的评分格式不兼容与重启

Gemini 全量比较已完成。FHIR 首次学习在开发阶段发现评分器不兼容，已停止并归档；尚未选定最终技能或测试 ID/OOD 集。旧参考函数要求 `ServiceRequest.note` 是对象，但 FHIR R4 的该字段是 Annotation 数组。13 次开发执行正确保存了最终有效订单，却因合法的单元素数组被判错。这些轨迹还包含一次先前回滚，因此修复后不能直接复用其不同的交互反馈路径。[FHIR R4 字段定义](https://hl7.org/fhir/R4/servicerequest-definitions.html#ServiceRequest.note)。

修订后的评分对所有方法采用相同的无损格式视图：单元素 note 数组转换为旧对象视图，仅含 text 的 route 对象转换为旧文本视图。文字和值不变；多元素注释和含编码的 route 不压缩。实际回读按同一规范化意图核对，直接工具方法仍提交原文；服务器正常转换 note 形状且保留字段时不判失败。真实字段丢失仍判失败。

保留原始评分，另报修订执行分数；不能称为未修改的官方基准分数。此次是评分与固定编译器修正，**不是 agent 进化收益**。已重查全部 13 次真实开发回执，正确内容通过、错误注释不通过、有效写入丢字段不通过；另有 8 项执行/兼容性测试通过。验证没有调用模型或新增真实写入。资源数已恢复为 695/21,991/563,426/0。

学习从空技能重新开始。仅允许复用提交内容和交互反馈完全一致、回读及清理成功的旧编译执行，并保留实际执行与费用来源。详见 `results/reference_revision_audit.json`、`results/grading_revision.json` 和修订协议。
