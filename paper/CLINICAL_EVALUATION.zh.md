# 从医生角度评价 RxRSIAgent 的处方

更新：2026-10-15。**状态：方案与评分工具已实现；尚无医生标注结果。** 这套指标补充主表的准确率／F1，不替换已有指标，也不把软件检查结果冒充临床质量。

## 1. 为什么要增加这些指标？

F1可以衡量预测药物和记录药物的重合，但无法单独说明：该处理的治疗目标是否遗漏、剂量与频率能否执行、是否加了没必要的药、是否需要监测或转交医生。不同药物方案也可能同样合理，不能只把历史处方当成唯一临床答案。

指标设计参考结构化用药审查与Medication Appropriateness Index（MAI）的研究思路；下列指标是本研究拟定的规则，**不宣称是一套已经验证的MAI变体或临床量表**。[NICE NG5](https://www.nice.org.uk/guidance/ng5/chapter/Recommendations)、[Hanlon等，1992](https://pubmed.ncbi.nlm.nih.gov/1474400/)

## 2. 三个主要临床终点

| 指标 | 怎么计算 | 防止什么误解 |
|---|---|---|
| **治疗需求覆盖率** ↑ | 满足的临床需求数／预先判定适用的需求数；另报关键需求覆盖 | 分母来自患者需要，不能只检查模型自己开出的药；适当暂缓或转交也可满足预定需求 |
| **严重错误病例率** ↓ | 至少有一项严重或潜在致命错误的病例数／已有明确严重错误判断的病例数 | 同时报未知比例；不是只统计DDI，也包括严重漏开、剂量、禁忌和处置错误 |
| **完整且临床正确的订单比例** ↑ | 所有适用字段均正确的订单数／已评估生成订单数 | 不把“字段都填了”当作正确；须与需求覆盖率一起看，不能少开药来抬高该指标 |

**临床需求**可以是应治疗的问题、应继续／调整／停止的用药、必要监测或必须转交的风险。评审者先依据决策时点可用的病例信息和来源冻结需求与可接受替代方案，再看模型输出。生成订单的具体检查项按预定规则展开；不能看哪个方法表现好，再改变规则。

## 3. 次要终点与错误分型

| 维度 | 指标与记录内容 |
|---|---|
| 不必要用药 | 无适应证、多余或不合理重复订单占比；同时报每例药物数 |
| 订单全面性 | 必需字段完整率；成分、剂量、单位、途径、频率、疗程分别的正确率 |
| 安全约束 | 对经过判定的风险测识别召回率、提示精确率、漏检和误报；按过敏、DDI、肝肾功能、人群限制分层 |
| 辅助用药与输液 | 用途是否成立；适用时配伍、溶媒、容量、浓度与速度是否正确；**不使用盐水出现F1** |
| 监测计划 | 必须的复查指标、时点、行动阈值覆盖率 |
| 证据支持 | 重要临床主张是否被引用资料支持，且药品／剂型／人群／时点适用；检索到片段本身不算通过 |
| 处置是否恰当 | 开药、续方、暂缓、补充信息、转交医生的选择是否正确；同时报实际开单覆盖率和未知率 |
| 用药核对 | 继续／新增／调整／停止的处理是否完整，包括相关非处方药 |
| 患者可执行性 | 给药能力、可获得性、患者目标与偏好是否满足 |
| 医生工作量 | 从草稿到可接受处方的修改数、修改类型和耗时；报告中位数与离散程度 |
| 资源 | 调用数、token、费用、延迟与无输出／拒答率；在相同预算下比较 |

将安全事件按预定规则分为：0无已识别错误、1轻微表达／记录问题、2需要临床修改但预期不构成严重危害、3潜在严重危害、4潜在致命危害。证据不足记为未知，不能当作0。这里评估的是潜在错误严重性，不是已经发生的患者伤害。

## 4. 分母、缺失与统计

- 对每项指标同时给出适用数量、完成评估数量、通过／失败／未知数量和评估覆盖率。
- 主结果按病例或患者平均；另给按需求／订单汇总的结果，避免药多的病例支配结论。同患者多次就诊用患者聚类。
- 缺失标注不自动算临床失败，也不算通过。工具同时给“已评估项通过率”和“已确认通过数／全部适用项”的保守下界。
- 不适用项不进入分母；零分母记NA。空订单的不必要用药率不记0%或100%质量分；结合需求遗漏和开单覆盖率解释。
- DDI／肾功能规则没有覆盖的情况单独报告，不能因查不到就判断安全。
- 使用同病例配对比较、患者级bootstrap区间，报告二分类一致率与严重度加权kappa。三个主终点若做确认性检验，需预先固定多重比较处理；其余按探索性分析报告。
- 不将所有指标加权成一个“综合安全分”，避免覆盖率提高掩盖严重错误增加。

## 数据集与病例边界

医生视角的完整处方评估拟使用 **MIMIC-IV3.1**，按真实记录可用时间重建决策时点信息；目标订单及事后信息不能作为actor输入。采样清单尚未生成，需先核对历史病例暴露并冻结患者名单，无法排除既往暴露的病例只能称探索性评价。现有[时间可用性记录](../upgrade_v20/RESULTS.zh.md)与[病例暴露核验](EXPOSURE.zh.md)提供重建依据。

该任务与主表的RxSafeBench／RxQA选项问答分开。问答题没有完整患者订单标签，不能凭回答正确就补出“临床处方全面性”。eICU可作为后续外部医院评测，须单独设定临床上下文与标注覆盖，不与MIMIC或QA分数合并。

## 5. 双人盲评如何执行？

已经有两位具备资质、可访问受限数据的评审者，后续可以提供结果；本次不需要重新确认。

1. **校准：** 另选20个病例统一需求、可接受替代、严重度和证据规则；不进入最终评测。
2. **主要队列：** 目标为100位随机抽取、信息适合此任务的患者。先记录纳入、排除和不可评估情况，不因模型失败删病例。
3. **挑战队列：** 另设50例，按输入中的肾功能问题、多药、特殊人群、辅助用药／输液等风险抽样，不按模型结果挑选；与随机队列分开报告。这是工作量规划，不是功效充分性的声明。
4. **比较方法：** RxRSIAgent、冻结技能／工具的对照，以及开发集预先选定的两个可运行外部agent，共4种配置；每例采用相同信息与预算。若有4种配置，则150例×4×2＝1,200份独立评价。
5. **盲法：** 隐去方法和检查点名称，统一格式，随机并平衡呈现顺序。评审者分别评分后才讨论分歧，保留原始评分；讨论后仍不能判断的保留未知。
6. **防泄漏：** 临床评测病例不进入训练反馈。用于选择更新的临床开发集与最终评测分离。受限病例、原始处方和身份映射只留本地；GitHub只放模板、代码、汇总和哈希。

## 6. 已交付的评分工具

[clinical_metrics.py](../rxrsiagent/clinical_metrics.py)可以汇总已判定的需求覆盖、严重错误和不必要订单标签，核验病例／订单清单，拒绝将尚未完成标注的模板生成正式结果。评审者原始表先保留，最终汇总输入标明`adjudicated`。它不会自动作出医学判断。

[7项合成测试](../rxrsiagent/results/clinical_metric_checks.json)覆盖漏项、缺失评价、空订单、关键风险未知、清单不一致、不适用项和未完成标注状态。工具尚不自动生成风险匹配、医生修改时间、kappa或置信区间；这些依赖后续真实标注与统计分析。

```bash
python -m rxrsiagent.clinical_metrics local_adjudicated_ratings.json local_summary.json
```

## 7. 如何接入RSI实验？

每个冻结轮次都用同一套终点定义评估，重点比较完整订单质量与严重错误是否同步改善。每次更新记录提议病例、修改对象、来源、被接受／拒绝理由和回归病例。模块实验分别固定其他组件，只替换技能、证据工具或订单工具；不把不同数据集上的收益拼成一个完整agent收益。

未来的临床开发反馈可以参与候选选择；最终医生测试评分不能回流学习。当前只有技能更新的完整轮次数据，其他模块的学习效果应分别补实验，不能把本次人工修复工具记成agent自主进化。
